## 当前基线

- 后端：LaunchAgent + 单进程 Uvicorn，监听 `127.0.0.1:8000`。
- 前端：LaunchAgent + Vite 开发服务器，监听 `127.0.0.1:5173`。
- PostgreSQL 16：Homebrew Service，仅监听本机。
- Redis：Homebrew Service，仅监听本机。
- `alis_data` 约 39GB，`alis_sim` 约 31MB。
- `dc_tushare_raw_records` 约 34GB、4528 万行。
- 数据卷使用率约 83%，剩余约 37GB。
- 当前没有已落地的自动数据库备份，WAL 归档关闭。
- 日更、模拟调仓、模型治理、人工复核和 Redis worker 均运行在后端进程内部线程。
- 当前业务时间统一使用 UTC+8。

## P0：资金与数据安全

### 1. 建立自动备份体系

- [ ] 准备外接 SSD、NAS 或对象存储作为备份目标。
- [ ] 完成首次 `alis_sim` 和 `alis_data` 全量备份。
- [ ] 配置 `alis_sim` 每日备份。
- [ ] 配置 `alis_data` 每周全量备份。
- [ ] 设计并启用 PostgreSQL WAL 归档，实现时间点恢复。
- [ ] 设置备份保留策略：最近 7 个日备份、4 个周备份、3 个长期备份。
- [ ] 增加备份 SHA-256 校验。
- [ ] 每月执行一次恢复演练，并保存恢复耗时与校验结果。
- [ ] 增加备份失败提醒。

验收标准：

- 两个数据库均可从备份恢复至独立测试库。
- 恢复后的核心表行数、最新交易日和账户数据校验通过。
- 备份不与生产数据库位于同一块物理磁盘。

### 2. 控制数据库和磁盘增长

- [x] 审计 `dc_tushare_raw_records` 的重复或功能重叠索引。（2026-07-22 完成只读审计；当前无可直接安全删除项，详见 [`PostgreSQL原始表索引审计-2026-07-22.md`](PostgreSQL原始表索引审计-2026-07-22.md)）
- [ ] 删除确认无业务依赖的冗余索引。
- [ ] 建立原始数据冷热分层策略。
- [ ] 将历史原始数据归档为 ZSTD Parquet。
- [ ] 为归档文件保存行数、时间范围、SHA-256 和 schema 清单。
- [ ] 验证归档后再删除在线数据库中的对应旧数据。
- [ ] 在线数据库仅保留近 12～18 个月高频原始数据。
- [ ] 为 `data_ingestion_runs` 设置 30～90 天保留期。
- [ ] 为 `dc_runtime_logs` 设置 30～90 天保留期。
- [ ] 配置每周 `VACUUM ANALYZE`。
- [ ] 增加表膨胀、死元组和索引增长监控。
- [ ] 增加磁盘 75%、85%、90% 分级告警和保护动作。

运行探针语义：`/api/live` 只表示进程存活；`/api/health` 和 `/api/ready` 表示正式运行就绪，未就绪时返回 HTTP 503，响应中的基础设施地址不包含认证信息。

验收标准：

- 数据卷长期保持在 75% 以下，或至少保留 30% 安全空间。
- 冷数据可通过归档文件复核，不影响日常查询和回测。
- 清理任务幂等、可审计，不会删除尚未成功归档的数据。

- [ ] 为应用账号按数据库和表授予最小必要权限。
- [ ] PostgreSQL 和 Redis 继续保持 localhost 或受控私网监听。
- [x] 服务器对外访问统一通过 HTTPS 反向代理。

- 应用数据库账号不能创建角色、创建数据库或修改系统配置。
- PostgreSQL 与 Redis 不能从公网直接访问。

## P1：长期运行可靠性

### 4. 将前端改为生产静态服务

- [ ] 停止使用长期运行的 Vite 开发服务器。
- [ ] 使用 `npm run build` 生成 `frontend/dist`。
- [ ] 使用 Nginx 或 Caddy 托管静态文件。
- [ ] 配置 SPA 路由回退。
- [ ] 配置静态资源缓存、gzip/brotli 和安全响应头。
- [ ] 将 `/api` 反向代理至后端服务。
- [x] 为 HTTPS 证书续期配置自动化。

验收标准：

- 生产环境不运行 Vite 或 Node 开发服务器。
- 页面刷新、前端路由和 API 访问均正常。

### 5. 拆分 API、调度器和后台 worker

- [ ] 新建独立 `alis-api` 启动入口，不启动后台调度线程。
- [ ] 新建独立 `alis-scheduler` 单实例入口。
- [ ] 新建独立 `alis-worker` 任务消费入口。
- [ ] 将日更、回测、训练、补数、归档等长任务迁移到 worker。
- [ ] 将自动调仓、模型治理和人工复核调度迁移到 scheduler。
- [ ] 为调仓增加数据库级唯一键或分布式锁。
- [ ] 为日更、训练、补数任务增加幂等键。
- [ ] 后端 API 支持 2～4 个 worker，而不会重复启动调度器。
- [ ] 服务重启后可恢复 running/pending 任务。
- [ ] 明确任务超时、取消、重试和死信策略。

验收标准：

- 多个 API worker 同时运行时不会重复日更或重复调仓。
- 终止 worker 后，未完成任务可由其他 worker 恢复。
- 每个交易日最多生成和执行一份正式调仓计划。

### 6. 优化日更和上游数据重试

- [ ] 将“上游未发布”从普通失败改为 `waiting_upstream`。
- [ ] 16:05 执行第一次检查。
- [ ] 数据未发布时采用 5～10 分钟退避，而不是持续高频完整采集。
- [ ] 19:30 后按 2～5 分钟检查，直到当日数据完整。
- [ ] 对连续失败使用指数退避和最大重试窗口。
- [ ] 当日数据完整后停止当日重试。
- [ ] 22:30 仍未完成时生成延迟告警。
- [ ] 次日 09:00 执行补偿检查。
- [ ] 聚合同一错误，避免每次重试都写入大段重复日志。
- [ ] 为不同 TuShare API 记录首次可用时间分布。

验收标准：

- 上游未发布不会造成大量失败运行记录。
- 数据一旦完整，系统能在下一次检查中自动生成计划并执行模拟调仓。
- 调度页面能显示等待原因、下次检查时间和最终完成时间。

### 7. 配置日志轮转和保留

- [ ] 后端 stdout/stderr 按天或大小轮转。
- [ ] 前端/反向代理日志按天或大小轮转。
- [ ] 单个日志文件限制在 50～100MB。
- [ ] 普通日志保留 14～30 天。
- [ ] 错误日志保留 90 天。
- [ ] 对重复错误进行时间窗口聚合。
- [ ] 数据库运行日志保存摘要，完整堆栈写入文件或日志平台。
- [ ] 增加日志目录磁盘占用监控。

验收标准：

- 服务连续运行一个月不会产生无限增长的单一日志文件。
- 关键错误仍能通过任务 ID、交易日和执行 ID 追踪。

### 8. 强化 Redis 持久化和队列可靠性

- [ ] 明确哪些 Redis Key 是缓存，哪些是不可丢失的任务状态。
- [ ] 为任务队列启用 AOF。
- [ ] 配置 `appendfsync everysec`。
- [ ] 保留 RDB 快照作为辅助恢复方式。
- [ ] 配置 Redis 内存上限和适当淘汰策略。
- [ ] 队列任务增加确认、超时领取、重试和死信机制。
- [ ] 定期清理已确认的历史 Stream 消息。
- [ ] 验证 Redis 重启后 pending 任务仍可恢复。

验收标准：

- Redis 非正常退出后，待执行任务不丢失。
- 缓存淘汰不会影响调仓、训练和补数任务的持久状态。

### 9. 优化 PostgreSQL 连接和运行参数

- [ ] 引入 PostgreSQL 连接池。
- [ ] 设置连接池最小、最大连接数和连接回收时间。
- [ ] 为 API 与 worker 使用独立连接池预算。
- [ ] 保留 statement timeout 和 connect timeout。
- [ ] 配置慢查询日志。
- [ ] 根据服务器内存调整 shared_buffers、work_mem 和 maintenance_work_mem。
- [ ] 监控连接数、锁等待、长事务和慢查询。

验收标准：

- 高并发读取不会为每次数据库操作重复建立物理连接。
- 后台大任务不会耗尽 API 可用数据库连接。

### 10. 改善进程守护和重复实例保护

- [ ] 为本机 LaunchAgent 增加合理的重启节流。
- [ ] 清理历史手动启动入口，避免与 LaunchAgent 抢占 8000/5173 端口。
- [ ] 启动前检测旧 PID 和端口归属。
- [ ] 服务退出时完成优雅关闭和任务状态持久化。
- [ ] 记录服务启动次数、退出原因和最近稳定运行时长。
- [ ] 在 Linux 上使用 systemd 的 `Restart=on-failure` 和启动限速。

验收标准：

- 日志中不再持续出现 `address already in use`。
- 服务异常退出后能自动恢复，但不会形成重启风暴。
